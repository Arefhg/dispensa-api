## 3. Decisions

New this week — `docs/DESIGN.md` §10 was created from scratch (PR #4), so every row in it is new:

| Decision | Why |
|---|---|
| Ledger instead of stored stock | Every stock number stays explainable; no silent overwrites |
| Recipes & sales pulled into the MVP (from v1.1) | Without recipes, staff's main job (recording sales) would be almost empty |
| Only the owner records deliveries | Owner handles supplier invoices and prices |
| Staff don't see ingredient stock or prices | Owner's choice — staff only need dish availability |
| Negative stock allowed | Real sales/waste must never be rejected; it's a signal something else (a delivery or count) is missing |
| Deactivate, never delete users | Keeps a record of who did what |
| Shared DB + `restaurant_id` | Simple to run and migrate; isolation enforced by one shared helper + tests |
| JWT 8h, no refresh token | Simple — one login per shift |
| PDF invoice uploads postponed | Needs storage, limits and backups not planned for v1.0 |
| Sync SQLAlchemy over async | Simpler code and tests; enough for the ~100-restaurant target scale |

Plus implementation decisions logged directly in `docs/WORKLOG.md`:

- `role`/`unit` stored as `String` + `CHECK`, not a Postgres `ENUM` — simpler to extend, avoids enum-alteration edge cases.
- `stock_movements.quantity` stays signed, with a per-type `CHECK` (`delivery > 0`, `sale < 0`, `waste < 0`, `correction != 0`) instead of one blanket positive check.
- Corrections store a server-computed delta (`counted − current_stock`) with a row lock (`SELECT ... FOR UPDATE`) to prevent races between concurrent stock counts.
- Test schema is built by running the real `alembic upgrade head` against `dispensa_test`, not `Base.metadata.create_all()` — so a broken migration fails tests too.
- `get_current_restaurant_id()` is the one explicitly-temporary source of tenant identity, wired to settings so it can be swapped for real auth in week 6 without touching routers.
- `mypy` set to `strict = true` from the first file, not relaxed-then-tightened later.

## 4. Learned

From `docs/WORKLOG.md`:

- Why a design review happens *before* code: the signed-quantity bug in `stock_movements` was caught as a paragraph in markdown, not as a migration already applied to a database.
- Pre-commit hooks run in their own isolated environment, separate from the project's `.venv` — mypy's `additional_dependencies` has to be kept in sync with what the code actually imports.
- `rev:` in `.pre-commit-config.yaml` and the matching package version in `pyproject.toml` are two independent pins that can drift apart if not moved together.
- Alembic's autogenerate reliably captures `CHECK` constraints on a table's *first* migration, but is known to miss changes to them later — hand-review matters most once tables already exist.
- SQLAlchemy naming-convention tokens `%(column_0_name)s` (first column only) vs `%(column_0_N_name)s` (every column) decide whether a composite unique constraint's generated name looks single-column.
- Ruff's `flake8-bugbear` (B008) flags `Depends(...)`/`Query(...)` as mutable defaults — that's FastAPI's intended pattern, fixed via `extend-immutable-calls` config, not a `noqa`.
- Filtering `(id, restaurant_id)` together in one query, rather than fetch-then-check, is what makes "wrong tenant" and "doesn't exist" both return the same plain 404.
- `mypy --strict` flagged `Settings()` as missing a required argument because it couldn't see `pydantic-settings` filling fields from the environment — fixed with the `pydantic.mypy` plugin, not a `type: ignore`.

## 5. Problems and fixes

From `docs/WORKLOG.md`:

- **`localhost` resolved to IPv6 `::1` on Windows**, which wasn't bound to anything, adding ~90s to every database command. Fixed by using `127.0.0.1` explicitly everywhere.
- **A generated migration kept failing `ruff format --check`** even after running `ruff format`. Root cause was an earlier command in the same `&&` chain exiting non-zero, so `ruff format` silently never ran — a shell-chaining mistake, not a code problem.
- **`mypy --strict` false positive on `Settings()`**, fixed via the `pydantic.mypy` plugin (see Learned above).
- **PR #4 and #5 were believed merged** based on a report, but `gh pr list` and `origin/main` showed them still open. Flagged the discrepancy, held off deleting branches, and re-verified before continuing.
